## Экономное делегирование

### Установленная система этого проекта

Superpowers 7.0.2 хранится в vendor/superpowers, ревизия 22f0b463e7a5e579904dd6211a520321035526f7.
Навыки обнаруживаются через локальные .agents/skills. Роли hackathon_scout и hackathon_reviewer определены в .codex/agents; их модели соответствуют экономным ролям ниже.
Порядок работы: бриф → короткий план → разработка в главной сессии → одно независимое ревью → проверки → демо.
По умолчанию применять executing-plans, а не запуск исполнителя и двух проверяющих на каждую мелкую задачу. Навыки читать по необходимости, не весь каталог сразу.
Лимит этой конфигурации: один открытый помощник, два запуска на ограниченную задачу. Пользовательские ограничения выше приоритетом процедур Superpowers. Исследователь и ревьюер не пишут код.
Пользователь отдельно разрешил учебный тест оркестрации experiments/agent-smoke до выдачи кейса. Для него достаточно существующего BRIEF.md: не начинать повторный brainstorming, не создавать worktree или коммиты. Два помощника проверяют учебный пример, главный исправляет его.


- Небольшие связанные задачи выполнять основной моделью.
- Самостоятельный ограниченный поиск по коду или документации: economy_explorer, gpt-6-luna, reasoning high.
- Одно итоговое ревью существенного изменения: economy_reviewer, gpt-6.1-sol, reasoning medium.
- Передавать короткое самодостаточное задание, fork_turns=none. Не наследовать весь чат.
- Не больше одного субагента одновременно и двух новых субагентов на ограниченную задачу разработки.
- Субагенты не создают других агентов; исследователь и ревьюер не редактируют файлы.
- Основная модель принимает архитектурные решения, решения по безопасности и проверяет выводы ревью.
- Повторное ревью только после исправлений или при конкретной нерешённой проблеме.
- При недоступности нужной модели продолжать основной моделью и сообщить об этом.
- Использовать текущую подписку ChatGPT; не подключать API-ключи, внешних провайдеров и платные модельные API для делегирования.

- Проверять бизнес-логику, основной путь, неверные входные данные, границы доступа и воспроизводимость запуска.
- Не писать тесты ради покрытия тривиальных конструкций; проверки должны ловить реальные отказы.
- Не выдавать синтетические данные, заглушки, выдуманные интервью или замеры за реальные результаты.
