# Разработка после выдачи задания

Стек выбирается по условиям и опыту команды. Готовые фреймворки оркестрации сравниваются в [MULTIAGENT_OPTIONS.md](../MULTIAGENT_OPTIONS.md).

## Первая рабочая версия

1. Создать репозиторий или согласовать уже существующий. Проверить доступ каждого участника.
2. Зафиксировать runtime и зависимости lock-файлом. В README указать точные команды запуска.
3. Согласовать вход, выход, ошибки и владельца каждого компонента.
4. Реализовать один путь целиком с примером данных.
5. Проверить запуск на втором компьютере, затем расширять функциональность.

## Передача задачи агенту

> Цель: [конкретный результат]. Контекст: [только необходимые файлы]. Область ответственности: [файлы/модуль]. Критерии готовности: [проверяемые условия]. Ограничения: [данные, стек, время]. Другие участники работают параллельно; не отменяй их изменения. Верни результат, команды проверки и ограничения. Не создавай других агентов.

Исследователю и ревьюеру дополнительно: «Только чтение, файлы не редактировать». Роли и модели — из AGENTS.md. Не отправлять им весь личный архив или историю чата.

## Объединение изменений

- Небольшая отдельная ветка на связанную задачу; для веток Codex использовать префикс `codex/`.
- Общие интерфейсы менять по договорённости, с обновлением потребителей.
- До объединения запускать проверки, относящиеся к изменению.
- Основная ветка должна сохранять рабочее демо. Перед крупным изменением знать, к какой версии можно вернуться.
- Не использовать автоматическое слияние и бесконечные циклы исправлений без проверяемого результата.
