### Решение о дополнительных моделях, 14 ноября

В основной путь пока не добавляем вторую модель для ещё одного балла. Модель извлекает факты и оценивает требования; версия политики в коде рассчитывает L/H, обязательность и порядок. Новая модель должна доказать снижение конкретной ошибки, а не просто согласиться с первой. Число вызовов остаётся `1 + 2 × число вакансий`; графики, сравнения и экспорт используют готовый отчёт.

[Локальный аудит исходников Nanimai](nanimai/REVIEW.md) показывает разделение анализа и числовой формулы: старая Platform 1.10 использовала YandexGPT lite для нескольких этапов, новая Platform 1.39 передавала анализ внешнему Tulpa и затем считала взвешенный балл со штрафами. Внутренности Tulpa и production-конфигурация не подтверждены; считать их ансамблем нескольких моделей нельзя.

Следующий эксперимент — отдельный разрешённый прогон на синтетическом E6 dev, проверенный E9 runner: обязательность, допустимые статусы, ссылки на доказательства, отношения порядка, опасные выводы и нагрузка ручной проверки. Ожидания команды остаются draft; отсутствие единственного эталонного порядка не отменяет проверку фактов. После разбора ошибок можно сравнить Luna/Sol на одинаковых случаях и решить, нужен ли второй проход только для спорных требований. Считать качество, задержку и стоимость отдельно; сохранить одинаковую политику балла. До такого сравнения преимуществ второй модели не заявляем. Ночью новые платные вызовы не разрешены и не выполняются.

Job Story: когда приходит кандидат, который может подойти нескольким открытым позициям, рекрутер хочет быстро увидеть основания выбора и оставшиеся вопросы, чтобы предложить подходящую альтернативу и передать менеджеру обоснование без повторного чтения всех документов. Основание — ответы заказчика 12 ноября; 10–20 минут сравнения и 10–15 минут оформления являются самоотчётом, не нашей измеренной экономией.

## Конкретный продукт к сдаче

1. **Вход и проверка.** Одно CV, набор вакансий; понятные имена, ошибки по файлам, ограничения до запуска; режим данных/модели виден.
2. **Контроль данных и требований.** Локальная защита, понятные замены, отдельный статус ручной проверки. Изменённые исходники делают старые подтверждения недействительными.
3. **Рейтинг с основанием.** Названия вакансий, состояние обязательных условий, L/H и полнота; почему одно место выше другого. «Риск/неизвестно» не спрятаны за зелёной цифрой.
4. **Рабочая таблица доказательств.** Требование → статус → цитата CV + цитата вакансии → контекст → что проверить. Фильтр спорного/неизвестного сокращает работу рекрутера.
5. **Результат менеджеру.** Рекомендация с оговорками, 2–3 основания, риски, 3–5 вопросов только по реальным пробелам; печать/HTML/Markdown. Число вопросов — максимум, не требование выдумывать недостающие.
6. **Дополнительная ценность при готовой базе.** «Какое уточнение может изменить порядок?» — what-if на фиксированной политике, явные допущения, без нового LLM-вызова и без изменения исходной оценки.

## Как доказываем качество без единственного правильного рейтинга

- Синтетические случаи по **frontend, учёту основных средств и образовательному процессу** — именно такие вакансии перечислены в условии. Python/Java — технический smoke, а не весь продуктовый набор.
- Для каждого случая: ожидаемые факты/основания, допустимые статусы и отношения между вакансиями при выбранной политике; неоднозначность помечена. Draft не называется ответом эксперта.
- Проверки фактов: каждая цитата существует и привязана к правильному источнику; нет неподтверждённых утверждений в финальном тексте; unknown не превращён в fail. Цель регрессионного набора: 0 нарушений этих инвариантов, это не обещание 100% точности на рынке.
- Проверки ранжирования: одинаковые входы/политика дают одинаковый расчёт; переименование файла/id не меняет смысловое место; изменение только имени/контакта не меняет профессиональную оценку; подтверждение неизвестного не ухудшает его вклад при прочих равных. Набор фиксируем до измерения.
- Отдельно измеряем **нагрузку ручной проверки**: доля needs_review, причины и сколько времени занимает подтверждение. Нельзя «добиться безопасности», отправив все строки на ручное перечитывание, и заявить ускорение.
- Сравнение с keyword baseline допускается на тех же случаях, с одинаковыми источниками и заранее указанными правилами. Показываем ошибки обоих методов и знаменатели, не выбираем только выигрышные примеры.
- Замер скорости: режим, SHA, ОС/CPU, N документов/символов, стадии, calls/usage/reserved/actual cost отдельно. Replay, CPU-проверка E3, cached rerank и live — четыре разных измерения. Малую выборку не называем p95 или SLA.

Целевые инженерные пороги, пока **не подтверждённые замерами**: офлайн пересчёт 20×80 требований без LLM <200 мс на ноутбуке команды; открытие готового отчёта <1 с после загрузки JSON; отсутствие повторных LLM-вызовов при смене отображения/сортировки; проверка всех входных ограничений до первого модельного вызова. Для свежего E2E сначала получить корректный baseline, затем оптимизировать измеренную медленную стадию.

## Скорость и полезные улучшения

Первое ускорение — кеш подтверждённых требований вакансии по source hash + schema/prompt/model/policy versions в одном разрешённом контексте. Повтор кандидата на неизменных N вакансиях может убрать N вызовов извлечения; это расчёт потенциального числа вызовов, не измеренный выигрыш секунд. Локальный what-if/пересортировка используют сохранённые факты, 0 API-вызовов.

Параллельные запросы — после корректного бюджета, отмены и сохранения частичного результата. Максимум 2 одновременно как начальный эксперимент; нельзя добавить asyncio.gather и потерять ограничение денег или продолжить запросы после privacy-инцидента. До этого полезнее реальные стадии прогресса и разумные лимиты вывода по типу ответа.

## Что сознательно откладываем

Многопользовательская ATS, HH-интеграция, отдельная векторная БД, несколько LLM-агентов в продукте, обучение модели, React-переписывание, облачный деплой с публичными резюме, OCR всех сканов. Это не запрет развития: эти функции не должны отнять время у 24 баллов сопоставления и 20 баллов воспроизводимости. OCR можно показывать как понятный отказ с рекомендацией файла с текстовым слоем.

Дальнейшее внедрение: локальный пилот с рекрутером и согласованными данными → измерение времени/ошибок на одинаковых задачах → роли/удаление/аудит → подключение потока вакансий. Не обещаем экономию, соответствие закону или промышленный SLA до проверки.
