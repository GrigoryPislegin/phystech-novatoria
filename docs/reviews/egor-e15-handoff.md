## Исправление 1: `mandatory_spans_segments`

Блок заголовка распознавался только для маркеров «-», «*», «•», «–», «—» и цифр. При «●», «·», «▪», «◦», «o», «✓», «+», «‣», «➢», «■», пунктах без маркеров, пустой строке под заголовком или заголовке без двоеточия каждая цитата «заголовок → пункт» отклонялась, все маркеры вакансии исключались, требования становились равными необязательными единицами. Отсюда «9 из 9» и «7 из 7» исключённых маркеров.

Теперь одна и та же вакансия с «- » и «● » даёт одинаковые нижнюю и верхнюю границы и состояние обязательных.

Строгие отрицательные тесты: пункт из «Будет плюсом» / «Желательно» / «Nice to have» (с двоеточием и без); пункт другого раздела; пустая строка внутри списка завершает блок; склеенная цитата, которой нет в вакансии, — `invalid`; короткая строка над обычным текстом заголовком не считается. Новое: заголовок, отрицающий обязательность («Необязательные требования», «Желательные навыки»), не может быть маркером — `mandatory_not_stated`.

## Исправление 2: «убедительный лидер» при тонких данных

Найдено: вакансия с одним частичным совпадением из восьми требований (6,25 пункта, покрытие 12,5%) рядом с вакансиями без данных получала `stable` и совет «проверьте лидера».

Правило `leader-0.2` в `scoring.py`: если засчитанные сведения покрывают меньше половины шкалы вакансии-лидера, первое место `open` с причиной `own_mostly_unknown`, рекомендация `clarify`, а решающими названы до трёх самых весомых неизвестных требований лидера. Текст: «лучший из мало изученных вариантов, а не установленный выбор».

- Порядок, оценки, веса 75/25 и `policy_version` не менялись: правило касается только того, называть ли первое место установленным.
- Правило про покрытие, не про балл: полностью известная слабая вакансия остаётся `stable`; подтверждённые обязательные при неизвестных желательных (покрытие 75) — тоже.
- Влияние на сценарии: набор E11 — 16 из 16, без изменений; демо success и disputed — прежние рекомендации.
- **Сохранённые отчёты.** Новые оценки помечены `score.leader_rules = "leader-0.2"`. Оценка без метки ранжируется и объясняется прежними правилами: отчёт, сохранённый раньше, открывается и не перечитывается (регрессия `StoredReportTests`).

Механизм из задачи на синтетике (`test_the_mechanism_of_the_changing_leader…`): при двух прочтениях одной вакансии порядок меняется (a, b → b, a), но оба раза итог `clarify / open`. Арифметика не скрывает нестабильность извлечения и не выдаёт её за уверенный выбор.

## Норма гранулярности требований — для Model (зона Codex)

Предложение для SYSTEM, без изменения wire:

1. Одно требование — одно проверяемое условие, на которое по резюме можно ответить одним из четырёх статусов.
2. Один пункт списка вакансии — одно требование. Делить пункт можно только на независимые условия, соединённые «и» или запятой («Python и Go» → два); не делить на уровень, стаж и название («Python от 3 лет» — одно).
3. Не склеивать разные пункты в одно требование и не повторять один пункт разными id.
4. Обязательность — только из текста: слово в самом пункте или заголовок его списка. Цитата обязательности — непрерывный фрагмент от заголовка до пункта включительно, как в вакансии, без пропусков. Нет явного указания — `mandatory_quote: null`.
5. Заголовки «Желательно», «Будет плюсом», «Условия», «Обязанности» обязательности не дают.
6. Число требований следует из числа пунктов: два запуска на одном тексте должны давать один список.

Признак для контроля без wire-change: отношение числа требований к числу пунктов-строк вакансии и число требований с одной и той же цитатой. Если понадобится поле, предлагаю `requirements_draft.granularity = {lines, requirements, shared_quotes}` — посчитаю в `requirements_review.py` по вашему сигналу.
