# E7 — почему вакансия А выше Б

13 ноября 2026, Егор. Задача #7, E7. Ветка `egor/e7-comparison` поверх расчёта v2 (PR #14 ← PR #8).

`prototype/ranking_explanation.compare(report, job_a, job_b) -> Comparison` — чистая функция на готовом `report.json`:
- без вызова модели и без новых фактов;
- ссылается только на существующие id требований, цитаты вакансий и цитаты фактов;
- не меняет отчёт;
- в pipeline не подключена (`INTEGRATED = False`).

What-if по ТЗ идёт после E5/E6. Здесь его нет, кроме проверки чувствительности (`swings`), описанной ниже.

## Как считается

- Для каждой вакансии функция заново вызывает `scoring.score` на требованиях, строках и evidence из отчёта:
  - если в `score` стоит `evidence_applied: true` — с evidence (политика v2);
  - иначе — так, как сейчас вызывает pipeline: маркеры из `score_review.excluded_mandatory_ids` сняты.

  Если пересчёт не совпал с отчётом по L, H, `coverage` или группе обязательных, функция выдаёт `score_not_reproducible`. Объяснение по чужой формуле не строится.
- Остальные отказы — `ValueError`:
  - `policy_mismatch` — балл посчитан не по `draft-2026-11-13-v2`;
  - `unknown_fact` — строка ссылается на несуществующий факт;
  - `incomplete_report` — нет нужных полей;
  - `unknown_job`, `same_job`.
- В отчёте v1 балл посчитан без учёта E3. Строки, которые E3 отправил на проверку, всё равно помечаются спорными (`disputed`), не входят в `deciding` и проверяются в `swings`. В этом случае добавляется оговорка `evidence_not_applied`.
- Порядок двух вакансий даёт сам `scoring.rank`, поэтому ничья, группа обязательных и L трактуются так же, как в рейтинге.

## Результат

| Поле | Значение |
|---|---|
| `outcome` | `a_higher`, `b_higher` или `tie` (общее место) |
| `reason` | `mandatory_violation` — нарушено обязательное только у нижней; `lower_bound` — выше L; `tie` |
| `scores` | место, L, H, `coverage`, группа обязательных обеих вакансий |
| `deciding` | До трёх строк, объясняющих разрыв, без спорных и неизвестных. Сначала проверенные `fail` по обязательным у нижней. Дальше зависит от списков:<br>— **одинаковый список и веса:** только различающиеся строки, по разнице вклада в L. `counterpart_status` — статус той же строки у другой вакансии;<br>— **разные списки:** сначала наибольшая потеря нижней, затем наибольший вклад, без пар.<br>При `tie` — пусто |
| `swings` | Неразрешённые строки (`unknown` или спорные), одно уточнение которых меняет порядок. У верхней проверяется `fail`, у нижней `full`, при ничьей у обеих `full`. Итог: `reversed`, `tie` или `breaks_tie`. Это чувствительность, а не прогноз ответа кандидата |
| `caveats` | `different_requirement_lists` — разные требования или веса обязательности, L не общая шкала; `incomplete_run`; `evidence_not_applied` |
| `summary` | Шаблонная строка из полей выше, без модели: группы обязательных обеих вакансий, «модель предложила у обеих несоответствие обязательному требованию» (модельный `fail` не выдаётся за факт), «Различия» при одинаковом списке, «Наибольший вклад» при разных |

Пример на `demo` (success), `compare(report, 'job-001', 'job-002')`:

```text
outcome a_higher, reason lower_bound; L 100 против 0
deciding: job-001 r1 «Python обязателен.» full, effect 75; job-001 r2 «SQL желателен.» full, effect 25
          (у job-002 Java — unknown, своих потерь нет; списки разные, поэтому «Наибольший вклад»)
swings:   job-002 r1 «Java обязателен.» unknown → full даёт tie
caveats:  different_requirement_lists
```

## Проверки

`prototype/tests/test_ranking_explanation.py`, 22 теста:
- причины `lower_bound` и `mandatory_violation`, ничья без `deciding`, перестановка аргументов зеркалит результат;
- при одинаковом списке в `deciding` только различающиеся строки; при разных списках первой идёт потеря нижней; все нарушенные обязательные стоят раньше больших вкладов;
- оговорка при одинаковых цитатах, но разных весах; текст ничьей называет группы обеих вакансий; «у обеих не выполнено»;
- в отчёте v1 спорные строки помечены, а в `deciding` не попадают;
- все ссылки существуют в отчёте, отчёт не меняется;
- спорная строка v2 считается открытой, отчёт v1 со снятым маркером воспроизводится, неполный запуск даёт оговорку;
- отклоняются: неизвестная вакансия, одна и та же вакансия, подделанный балл, чужая версия политики, ссылка на несуществующий факт, неполный отчёт;
- 300 случайных отчётов: `outcome` совпадает с местами отчёта, а набор `swings` равен независимо пересчитанному — ни одна строка не пропущена и ни одна не лишняя.

Мутационная проверка — разовым скриптом вне репозитория, поэтому повторить её из ветки нельзя. 16 правил по очереди отключались, каждое ловится тестами. Две мутации сначала выжили: одна показала лишний код (убран), другая — непокрытый случай (добавлен тест).

Независимое ревью нашло пять проблем, все исправлены с тестами:
- `deciding` показывал наибольший вклад вместо различий;
- в отчёте v1 спорные строки не помечались;
- текст ничьей и случая «обе нарушили» вводил в заблуждение;
- оговорка не учитывала веса, версия политики не проверялась;
- неполный отчёт падал с `KeyError`.

## Ограничения

- Рассматриваются только одиночные уточнения. Две неизвестные строки, которые меняют порядок только вместе, в `swings` не попадут.
- Случайный тест сверяет `swings` с пересчётом по тому же правилу (одно уточнение до крайнего статуса). Это ловит ошибки реализации, но не проверяет само правило.
- `effect` — вклад в L при прочих равных, а не причинность и не вероятность.
- Сравнение верно ровно настолько, насколько верны статусы модели: смысл строк не проверяется (`model_claim_unverified`).
