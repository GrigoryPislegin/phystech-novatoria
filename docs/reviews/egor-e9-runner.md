# E9b — проверка сохранённых отчётов против E6

14 ноября 2026, Егор. Задача #20. Ветка `egor/e9b-evaluation-runner` от `codex/cli-integration-consultation` `aeb0429`.

```sh
python -m evaluation.runner --reports DIR \
    --expectations evaluation/expectations/egor/e6-cases.json --split dev --out OUT
```

Раннер не обращается к модели, сети, ключам и `.env`. Он читает готовые отчёты pipeline и сверяет их с ожиданиями E6. Фактические значения берутся только из отчётов: из ожиданий раннер их никогда не строит.

## Вход

`DIR/manifest.json`:

```json
{"mode": "synthetic_replay" | "sdk_mock" | "live",
 "reports": {"E6-FE-01": "E6-FE-01.json", "E6-FE-02": "E6-FE-02.json"}}
```

- **Один случай — один `report.json`** обычного pipeline (`schema_version 0.1`). Отчёт строится на `cv_text` и `vacancies` случая.
- **Режим обязателен и в манифесте, и в каждом отчёте.** Значения CLI сопоставляются явно:
  - `synthetic_replay_NOT_model_output` → `synthetic_replay`;
  - `synthetic_sdk_mock_NOT_model_output` → `sdk_mock`;
  - `live_synthetic`, `live_local_privacy` → `live`.

  Отчёт без `mode`, с неизвестным `mode` или с режимом, отличным от манифеста, — отказ (exit 2). Смешанные режимы не усредняются.
- **Однозначное соответствие.** Повтор ключа в JSON, два случая на один файл, `reports` не объектом — отказ (exit 2).
- **Только `live` измеряет качество модели**, и только если хотя бы один отчёт действительно оценён. `synthetic_replay` и `sdk_mock` проверяют pipeline и сам раннер. Тогда, как и при live без пригодных отчётов, `quality_measured: false` и «качество модели не измерено».
- **Путь отчёта** вне `DIR` отклоняется (exit 2).
- **Необработанные вакансии.** Для случаев с `unprocessed_job_ids` (ED-04, ED-05) вакансия должна действительно упасть в pipeline (попасть в `unprocessed`). Иначе случай получает `expected_failure_not_reproduced`.

`--split dev` — по умолчанию. `--split holdout` включается только явно и только если SHA-256 holdout совпадает с `holdout.sha256`, иначе exit 2.

## Проверки одного случая

| Шаг | Что проверяется | Исход |
|---|---|---|
| Настройка | Есть отчёт-объект, `schema_version 0.1`. Форма самого отчёта проверяется до метрик и без чтения ожиданий: уникальные id фактов, вакансий, требований, строк и необработанных; статус из четырёх; строки покрывают требования; `rank` — целое от 1 до числа вакансий. Набор вакансий совпадает со случаем, ожидаемый сбой воспроизведён | Иначе `missing_report`, `unreadable_report`, `unknown_report_version`, `malformed_report` (любая битая структура — не traceback), `duplicate_*_ids`, `invalid_row`, `invalid_rank`, `rows_do_not_cover_requirements`, `job_set_mismatch`, `expected_failure_not_reproduced`. Ничего не оценивается, но **каждая** проверка случая (строки, пары, рекомендация, условия, ссылки) остаётся в списке «не измерено» с этим кодом |
| Сопоставление | Требования сопоставляются один к одному по пересечению цитат в тексте вакансии; при равенстве выигрывает более длинное пересечение, затем более раннее ожидаемое | Без пары → `missed_requirement`; лишние извлечённые — `extra_requirements` (счётчик) |
| Строка | Отдельно: статус не запрещён (`status_ok`); цитируемый факт хотя бы наполовину лежит внутри ожидаемой цитаты и E3 не `invalid` (`evidence_ok`, для `unknown` не применяется); обязательность совпадает (`mandatory_ok`) | Итог: `wrong_mandatory` / `wrong_status` / `wrong_evidence` / `pass`. Неожиданный сбой вакансии → `error`, никогда не `unknown`. Строка без проверки (пропущенное требование, сбой) остаётся в метриках корректности как «не измерено» со своей причиной |
| Ссылки | Цитаты фактов есть в резюме, цитаты требований — в вакансии, `fact_ids` существуют | `references_valid` |
| Порядок | Каждая пара `better`/`worse`: строго выше или не ниже. Единственный порядок не требуется | `pass` / `fail` / `unmeasured` (вакансия не обработана) |
| Рекомендация | Входит в допустимые | `pass` / `fail` |
| Условия | Состояние условия в `job.conditions` входит в допустимые | Нет `conditions` → `not_run` |
| Запреты | `forbidden_conclusions` | Только ручная проверка, считается `manual_checks` |

## Метрики

У каждой метрики есть `numerator`, `denominator`, `value`, `failures` (случаи) и `unmeasured` (случай:причина). Пустой знаменатель даёт `value: null`, что выводится как «не измерено», а не 100%.

| Метрика | Что входит в знаменатель |
|---|---|
| `cases_evaluated` | Все случаи сплита; пропущенный или негодный отчёт — провал полноты |
| `rows_without_processing_error` | Ожидаемые строки обработанных случаев, кроме ожидаемо необработанных |
| `requirement_extraction_coverage` | Те же строки без ошибок обработки |
| `status_allowed` | Строки с парой |
| `evidence_matches_expected_quote` | Строки с парой и допустимым известным статусом |
| `mandatory_marking` | Строки с парой |
| `row_fully_correct` | Строки с парой: все три признака верны |
| `rank_relations` | Пары порядка, где обе вакансии обработаны |
| `recommendation_allowed` | Оценённые случаи |
| `conditions` | Ожидания условий, по которым есть `job.conditions` |
| `references_valid` | Оценённые случаи |
| `equivalent_wording_consistent` | Группы эквивалентности, в которых оценены минимум два члена |

`by_domain` повторяет `status_allowed` и `row_fully_correct` по областям: frontend, учёт ОС, образование.

Отдельно, без долей:
- `review_load`: пункты очереди E8, строки `unknown` и `fail`, спорные строки E3, конфликты условий;
- `extra_requirements`;
- `manual_checks`.

Это нагрузка ручной проверки и найденные противоречия, а не качество. Доли — это прошедшие проверки по черновым ожиданиям команды (`decision_status: draft` в каждом результате), а не вероятность истинности и не оценка эксперта.

## Выход

`OUT/evaluation.json` содержит все случаи с исходами каждой строки, пары, условия и нагрузку. `OUT/evaluation.md` — короткая таблица. Exit-коды: 0 — оценено, даже если всё «не измерено»; 2 — отказ: манифест, режим, holdout, путь.

На пустом наборе отчётов (сейчас живых ответов нет) получается `cases_evaluated 0/10`, остальное «не измерено».

## Тесты

`prototype/tests/test_evaluation_runner.py`, 31 тест. Отчёты в них строятся настоящим `run_pipeline` с моделью, ответы которой записаны вручную, а не взяты из ожиданий.

- **Принимается:** хорошие ответы проходят все измеренные проверки; допустимые альтернативы (FA-02 `fail` и `partial`) принимаются; настоящий сбой вакансии в ED-04 даёт `incomplete`.
- **Ловится ложный идеальный результат:**
  - запрещённый статус;
  - переставленная обязательная пара;
  - ничья при строгой паре;
  - пропущенный случай;
  - пустой результат;
  - неверная ссылка;
  - чужое доказательство;
  - неверная обязательность;
  - невоспроизведённый ожидаемый сбой;
  - неожиданный сбой как `error`;
  - расходящиеся формулировки в группе;
  - файл ожиданий вместо отчёта;
  - неверное условие;
  - пропущенный случай остаётся «не измерен» во всех метриках;
  - факт-абзац на всё резюме не считается доказательством;
  - битые отчёты и манифесты;
  - группа из одного члена;
  - смешанные режимы и отчёт без режима;
  - пустой или испорченный holdout;
  - путь вне каталога.

  Принимаются названия режимов CLI, включая `synthetic_sdk_mock_NOT_model_output`. Повторы id, неизвестный статус, неверный `rank` и live без пригодных отчётов не дают «измерено».

Мутационная проверка — разовым скриптом вне репозитория: 22 правила раннера по очереди отключались, каждое ловится. Одно лишнее правило (дубль `errors`/`unprocessed`) мутация показала, и оно убрано.

Независимое ревью нашло 4 проблемы, все исправлены с тестами:
- пропущенный случай выпадал из метрик корректности, и они показывали 100%;
- защита по режиму не работала, а настоящие режимы CLI отклонялись;
- битый ввод давал traceback;
- «любое пересечение» засчитывало факт-абзац как доказательство. Правило ужесточено и в `egor-e6-cases.md`.

## Ограничения

- Живых ответов модели нет, поэтому качество модели не измерено. Чтобы измерить, нужен отдельный разрешённый прогон `live` на синтетических текстах E6: это решение Григория и бюджет продукта.
- Запрещённые выводы проверяются вручную.
- Профиль кандидата E6 не размечает: отрицание в профиле раннер не ловит.
- Сопоставление по пересечению цитат не узнает требование, если модель процитировала другое место вакансии.
