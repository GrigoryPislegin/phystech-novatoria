## 1. [Высокий] Обязательность можно приписать не тому требованию

**Где:** `contracts.py:23-28`, `contracts.py:17`, `scoring.py:19-22`.
`validate_source` проверяет только одно: строка `mandatory_quote` встречается где-то в тексте вакансии. Связь цитаты с самим требованием не проверяется, как и то, что она вообще говорит об обязательности. Принимается даже цитата из одного символа.

**Пример (синтетика).** Вакансия: `Python обязателен. SQL желателен.` Резюме: Python 3 года, SQL 1 год. Модель ставит `r1 Python → mandatory_quote=None`, а `r2 SQL → mandatory_quote='Python обязателен.'`. SQL оценён как `fail`.

| Разметка | L / H | mandatory | Рекомендация |
|---|---|---|---|
| Ошибочная, проходит валидацию | 25 / 25 | violated | `review_none_fit` |
| Правильная | 75 / 75 | confirmed | `review_top` |

Вариант `mandatory_quote='л'` тоже проходит и даёт вес 3.

**Последствия.** Желательный навык превращается в «обязательное нарушение», вакансия опускается в конец списка, а для набора из одной вакансии система предлагает рассмотреть отказ. В `report.md` не видно, какое требование стало обязательным и по какой цитате. Поэтому рекрутер не заметит ошибку.

**Предложение.**
- Требовать, чтобы `mandatory_quote` перекрывал `quote` своего требования или был заголовком его блока («Обязательные требования:» перед пунктом).
- Задать минимальную длину цитаты.
- В отчёте у каждого обязательного требования показывать «обязательно: «…» (предложено моделью, подтвердите)».
- Регрессионный тест: пример выше должен давать `ValueError`, а `Python и SQL обязательны.` с двумя требованиями должен проходить.

## 2. [Высокий] Fail может опираться на постороннее доказательство: «не указано» превращается в «не соответствует»

**Где:** `contracts.py:75-81`, `pipeline.py:33-34`, промпт `model.py:17-18`.
Для `fail` достаточно любого существующего `fact_id`. Связь факта с требованием не проверяется. Разница между unknown и fail держится только на промпте. Кроме того, оценщик получает `Fact.text`, то есть пересказ модели, который с цитатой не сверяется.

**Пример (синтетика).** Требование `Java обязателен.` Строка: `status='fail', fact_ids=['f1']` (f1 — «Python 3 года»), комментарий «Пишет на Python, а не на Java». `validate_pair` пропускает. Результат: L=0, H=0, coverage=100, `violated`. При правильной разметке было бы `unknown`, L=0, H=100, `clarify`.

**Последствия.** Происходит то смешение, которое эксперт просил различать: отсутствие сведений засчитывается как несоответствие (docs/12, п. 4). Вакансия уходит вниз. Если так случится во всех вакансиях, появится `review_none_fit` там, где нужен вопрос кандидату. Цитата при этом настоящая, поэтому отчёт выглядит доказательным.

**Предложение.** Полностью закрыть это кодом нельзя (docs/15 §5 это признаёт), но риск можно сделать видимым:
- передавать оценщику факты только как `{id, quote}`;
- для каждой строки `fail` по обязательному требованию выводить в отчёт пару «цитата требования ← цитата факта» с пометкой «гипотеза модели»;
- в ручной проверке качества отдельно считать долю `fail`, которые должны быть `unknown`;
- тестом зафиксировать, что такой вход сейчас проходит, — как известное ограничение.

## 3. [Средний] Одинаковое место при разной известности: «ничего не знаем» = «точно не подходит»

**Где:** `scoring.py:30-38`. Порядок и равенство считаются только по `(violated, L)`. H и coverage на место не влияют.

**Пример (синтетика).** Две вакансии, у каждой по два желательных требования.

| Вакансия | Статусы | L / H / coverage | Место |
|---|---|---|---|
| A | unknown, unknown | 0 / 100 / 0 | 1 |
| B | fail, fail | 0 / 0 / 100 | 1 |

Обе получают место 1, порядок внутри места определяется по алфавиту id. Похожий случай: «сильный, но неполный» (L=50, H=100) стоит ниже «слабого, но полного» (L=60, H=60).

**Последствия.** Формально это соответствует §6 («равные L — одно место»). Но рекрутер видит вакансию с доказанными несоответствиями на том же месте, что и вакансию, по которой просто нужно задать вопросы. Требование приёмки «unknown отличается от fail» выполняется в числах L/H, но не в рейтинге.

**Предложение.** Это продуктовое решение, вынесено в вопрос 2 консультации. До ответа можно, не меняя формулу, внутри одного места показывать сначала вакансию с большим H и писать в отчёте: «одинаковое место; у A не хватает данных, у B подтверждены несоответствия».

## 4. [Средний] Отчёт не содержит части того, что подтвердил эксперт

**Где:** `pipeline.py:64-79`.
По docs/12 нужны сильные стороны относительно вакансии, пробелы и риски, рекомендации рекрутеру, вопросы кандидату и обоснование порядка. Сейчас:
- строка «Сильные стороны: строки full; частичное соответствие: partial; пробелы/риски: fail и unknown.» — **одинаковый шаблон** для всех вакансий (в демо он повторяется 3 раза), а не список требований;
- рекомендация по конкретной вакансии тоже шаблонная;
- нет текста, объясняющего, почему вакансия на этом месте и какая вакансия рекомендуется в итоге: есть только код `review_top`;
- обязательные требования в таблице не помечены. В демо у job-001 не видно, что Python обязателен: это есть только в CSV;
- вопросы разбросаны по строкам, сводного блока для кандидата нет.

**Пример.** `python -m prototype demo` → `report.md`, раздел job-001.

**Последствия.** На демонстрации эксперт увидит таблицу, но не увидит четырёх подтверждённых им блоков. Именно этот отчёт рекрутер передаёт менеджеру.

**Предложение.** Всё это можно собрать кодом из уже проверенных строк, без новых вызовов модели:
- «Сильные стороны: <full>», «Частично: <partial>», «Риски: <fail>», «Нет данных: <unknown>»;
- пометка «обязательное» с цитатой;
- блок «Вопросы кандидату»;
- строка обоснования места («нет нарушений обязательных, L=…, известность …%»);
- итоговая строка «Рекомендуем посмотреть: job-… потому что …».

Регрессионный тест — проверка этих строк в демо-отчёте.

## 5. [Средний] Неполный прогон плохо виден рекрутеру

**Где:** `pipeline.py:26-27, 39-45, 79`; `__main__.py:57-59`.

**Пример (синтетика).** Демо-набор, модель падает на оценке второй вакансии. `report.json` верно ставит `incomplete` и `unprocessed_job_ids=['job-002','job-003']`. Но в `report.md` нет ни `job-002`, ни `job-003`, только «Есть ошибки: рейтинг неполный. Подробности в report.json.» В `errors` не записана стадия (требования / оценка / валидация).

Если на этапе фактов модель вернёт несуществующую цитату, `run_pipeline` бросит `ValueError` до цикла. Тогда не будет ни отчёта, ни стадии ошибки, CLI выведет только общее сообщение.

**Последствия.** Рекрутер, читающий Markdown, видит одну вакансию и может принять её за полный результат. При разборе ошибок непонятно, какой шаг сломался. При этом docs/15 §7–8 требуют сохранять ошибку с кодом и стадией и отмечать необработанные позиции.

**Предложение.**
- Добавить `stage` в запись ошибки.
- В `report.md` выводить «Ошибка: job-002 (стадия)» и «Не обработаны: job-003».
- Ошибку на этапе фактов сохранять как отчёт с пустым рейтингом и кодом `facts_failed`.

## Не вошло в пятёрку

- Дублирование требования (`contracts.py:20-28`). Два требования с одинаковыми `text` и `quote` проходят валидацию, вес Python становится 6 вместо 3. Это подтверждено синтетикой. Ниже по приоритету: влияет на вес, но не меняет статус.

## Что проверено и работает по спецификации

- `unknown` не может иметь доказательств, остальные статусы обязаны их иметь. Для каждого статуса кроме `full` обязателен вопрос.
- L/H/coverage совпадают с примером §6 (75/100/75 и 75/75/100). W=0 недостижим. Нарушение обязательного требования не штрафуется дважды.
- Ворота обязательности: fail → violated; partial/unknown → clarify; все full → confirmed; нет обязательных → not_set.
- Неполный набор вакансий всегда даёт `incomplete`, а не `review_none_fit`. Если все обязательные требования unknown, результат — `clarify`. Пустые факты дают только unknown и `clarify`.
- Защита всех документов выполняется до первого вызова модели. После ошибки следующие вызовы не делаются.

## Не проверено

- Качество live-модели: как часто она выдаёт входы из п. 1–2. Без ключа и разрешённых данных это не измерить.
- Сортировка смеси violated и не-violated при равном L. Не покрыта тестом, но код ведёт себя по спецификации.
- Полнота извлечения требований и фактов.
- Certum, парсинг документов (зона Вани) и приватность.
