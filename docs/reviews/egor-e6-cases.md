## Формат случая

```text
case_id, domain, split (dev | holdout), covers[], decision_status, equivalence_group, open_question
cv_text                      — обработанный текст резюме
vacancies[] {job_id, text}
unprocessed_job_ids[]        — вакансии, для которых раннер должен получить ошибку обработки
requirements[] {job_id, key, quote, mandatory, allowed_status[], forbidden_status[], cv_quotes[], rationale}
conditions[] {job_id, kind, allowed_states[], rationale}
ranking {relations[] {better, worse, strict}, allowed_recommendations[]}
forbidden_conclusions[]      — текст для ручной проверки отчёта
```

- `key` — наш ключ, не id модели.
- `allowed_status` и `forbidden_status` вместе дают все четыре статуса.
- `cv_quotes` — основание для известного статуса: пусто, если допустим только `unknown`; непусто, если допустим хоть один известный статус.

## Как раннеру судить сохранённый отчёт

**1. Сопоставление требований** — один к одному.
- Извлечённое требование соответствует ожидаемому, если их цитаты пересекаются по позиции в тексте вакансии.
- Если одно извлечённое пересекает два ожидаемых, оно достаётся тому, с кем пересечение длиннее. При равенстве — тому, что стоит раньше в тексте. Второе ожидаемое остаётся без пары.
- Ожидаемое без пары — `missed_requirement`. Это ошибка извлечения, не `unknown`.
- Лишнее извлечённое — `extra_requirement`.

**2. Исход строки**, первый подходящий:

| Исход | Когда |
|---|---|
| `error` | Вакансия в `errors` или `unprocessed`, хотя случай этого не ожидает. Все ожидаемые строки этой вакансии получают `error` |
| `missed_requirement` | Нет пары |
| `wrong_mandatory` | Обязательность не совпала с `mandatory`: `mandatory_quote` есть, когда не должен, или нет, когда должен |
| `wrong_status` | Статус в `forbidden_status` |
| `wrong_evidence` | Статус допустим, но E3 дал `invalid` либо ни одна цитата факта не пересекается ни с одной из `cv_quotes`. Для `unknown` не применяется |
| `pass` | Иначе |
| `not_run` | Живого ответа нет |

Ошибка обработки никогда не засчитывается как правильный `unknown`.

**3. Ожидаемо необработанные вакансии.**
- Раннер передаёт в pipeline модель, которая для этих вакансий выдаёт ошибку. В отчёте вакансия должна оказаться в `errors` и `unprocessed`, рекомендация — `incomplete`.
- Если вакансия всё-таки обработана — исход случая `setup_error`, рейтинг не оценивается.
- Простое исключение вакансии из `rank` проверяет только счётчик, этого недостаточно.

**4. Уровень случая**, отдельные знаменатели:
- `relation_pass` / `relation_fail` — по каждому `relation`;
- `recommendation_pass` / `recommendation_fail`;
- `group_consistent` / `group_inconsistent` — статусы по каждому `key` в группе эквивалентности;
- `condition_pass` / `condition_fail` / `not_run` — до подключения E5 `Conditions` всегда `not_run`;
- `forbidden_conclusions` — только ручная проверка, автоматически не засчитываются.

**5. Отчёт раннера.**
- Отдельно dev и holdout, отдельно по областям.
- Число ожидаемых строк и каждого исхода из п. 2, число `extra_requirement`, уровень случая из п. 4.
- Без живых ответов модели — «не измерено». Сохранённый replay написан вручную и качество модели не измеряет.
- Обязательная проверка самого раннера: подложенный отчёт с допустимым статусом и неверной цитатой должен дать `wrong_evidence`, а не `pass`.

## Holdout

- Шесть случаев, по два на область: FE-03, FE-06, FA-03, FA-05, ED-02, ED-05.
- Ключевые поведения есть и в dev, и в holdout, обычно в разных областях:
  - отрицание: FE-02 / FA-05;
  - пересечение сроков: FA-02 / FE-06;
  - неполный запуск: ED-04 / ED-05;
  - синонимы: FA-01 / FE-03;
  - `unknown` против `fail`: FE-01 / FA-03, ED-05.
- SHA-256 канонического JSON записан в [`holdout.sha256`](../../evaluation/expectations/egor/holdout.sha256), тест падает при любой правке.
- Holdout зафиксирован в первом коммите этого файла, раньше раннера и любого прогона. До коммита его один раз пересобрали по итогам ревью (до любого прогона).
- Веса и правила не подстраиваются под holdout. Если ожидание holdout поменялось по существу (например, после ответа эксперта), меняется хеш. Причина пишется в коммит, а результаты до и после не сравниваются как один прогон.

## Что проверено без модели

`prototype/tests/test_e6_expectations.py`, 10 тестов:
- **Формат.** Не меньше 12 случаев и не меньше 4 на область, все метки покрытия, ключевые метки в holdout, все `draft`.
- **Цитаты.** Цитаты требований встречаются в вакансии ровно один раз, цитаты резюме есть в резюме, правило `cv_quotes` соблюдено.
- **Согласованность с политикой.** Перебраны все комбинации допустимых статусов. Каждая даёт допустимую рекомендацию и выполняет отношения мест. Ожидания не требуют от политики невозможного.
- **Группы эквивалентности** имеют одинаковые ожидания. **Holdout** не изменён.
- **E3 на правильных цитатах.** Невалидных доказательств нет. На проверку уходят только строки случаев с синонимами или с подтверждающим предложением без общего термина. Улучшение E3 этот тест не ломает.

### Измерение: E3 на правильных цитатах

Ожидаемые цитаты прогнаны через `check_pair` с первым допустимым статусом. Из 34 строк 5 уходят на проверку с `evidence_not_linked`:

| Случай | Требование | Почему |
|---|---|---|
| FE-03 | TypeScript | «TS» |
| FA-01, FA-02 | стаж ОС | «ОС», «учёт» против «учёта» |
| ED-03 | высшее образование | «педагогический университет» |
| ED-05 | организация процесса | Даты стоят в отдельном предложении «Методист вуза, 2018–2023» без общего термина |

Это цена осторожного правила связи по общему термину: по политике v2 такие строки не попадают в L, пока рекрутер их не проверит. Ложных `structure_ok` здесь не видно, но набор слишком мал для оценки. Словарь синонимов не предлагаю: ТЗ запрещает подменять смысл списком слов. Вариант для решения — метка «возможный синоним» в очереди проверки E8.
