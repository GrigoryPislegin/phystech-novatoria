# E7 — what-if: что изменится, если уточнить одно требование

14 ноября 2026, Егор. Отложенная часть задачи #7. Ветка `egor/e7-what-if` от `codex/cli-integration-consultation` `7947ccb`.

`prototype/what_if.py` — чистая функция на готовом отчёте:
- без вызова модели, без записи и без новых фактов;
- оригинальный отчёт, оценку модели и решения HR не меняет (это проверяется, при нарушении — `RuntimeError`);
- `scoring.py`, `ranking_explanation.py`, pipeline и UI не менялись: what-if только переиспользует их.

```python
what_if_options(report) -> list[Option]   # открытые требования, по одному на единицу требования
what_if(report, job_id, requirement_id, assumed_status) -> WhatIf
```

## Правила

- **Что можно спросить.** Только открытое требование: статус `unknown`, `needs_review` по E3 или `disputed_ids` политики. Проверенный `full`, `partial` или `fail` — это утверждение модели для проверки, а не вопрос what-if (`not_open`).
- **Единицы требований (v3).** Дословные повторы — одна единица:
  - она предлагается один раз (`requirement_ids` — все её строки), спросить можно через любую строку;
  - допущение применяется ко всем строкам единицы;
  - открыта ли единица, решает её состояние в политике: `unknown`, `disputed` или `conflict` (в H, не в L);
  - единица, которая уже входит в L (например, `full` и повтор без данных), закрыта: `not_open`;
  - повторы с разными известными статусами показываются как `status: conflict`, даже если политика называет единицу `disputed` (оба повтора на проверке).

  В v1/v2 единица — одна строка.
- **Одна политика.** Все вакансии и сам отчёт должны называть одну политику (`policy_mismatch` иначе, как в `compare`). `policy_version` ответа — политика отчёта, а не текущая версия кода. Пересчёт идёт через `_Job.rescore` той же политикой.
- **Допущение.** `full` / `partial` / `fail` — допущение для уточнения у кандидата, а не прогноз его ответа. `unknown` как допущение не принимается.
- **Та же формула.**
  - Балл вакансии пересчитывается на тех же входах, которыми `ranking_explanation` воспроизводит балл отчёта. Строка считается структурно подтверждённой с допущенным статусом.
  - Потом все вакансии запуска заново ранжируются через `scoring.rank` с ожидаемым числом вакансий запуска, поэтому неполный запуск остаётся `incomplete`.
  - Отчёт должен воспроизводиться целиком, иначе он отклоняется:
    - балл **каждой** вакансии (`score_not_reproducible`, `policy_mismatch`);
    - места и рекомендация исходного рейтинга при том же `scoring.rank` (`ranking_not_reproducible`).

    Иначе «разница» показывала бы расхождение кода, а не эффект допущения. Битый отчёт — `incomplete_report`, а не сырой `KeyError`.
- **Неполный запуск.** Необработанные вакансии в мест не получают, есть оговорка `incomplete_run`. Отчёт с `complete: false` без списка `unprocessed` тоже остаётся `incomplete`.
- **Общее место.** Оно называется явно — «2 → 1 (общее с job-001)», — чтобы ничья не выглядела как обгон.

## Ответ

| Поле | Значение |
|---|---|
| `kind` | всегда `hypothetical` |
| `policy_version` | политика, которой посчитан отчёт |
| `assumption` | вакансия, требование и все строки его единицы, цитата, исходный статус (в т.ч. `conflict`), был ли спор, допущенный статус |
| `baseline` / `alternative` | места всех обработанных вакансий, рекомендация, L/H/`coverage`/группа обязательных этой вакансии |
| `affected_ids` | вакансии, чьё место меняется |
| `caveats` | `incomplete_run`, `different_requirement_lists` |
| `summary` | шаблонная строка, всегда с оговоркой «это допущение для уточнения у кандидата, не ответ кандидата и не решение» |

Пример на demo «спорный»: `what_if(report, 'job-002', 'r1', 'full')`:
- места: job-002 2 → 1, job-001 1 → 2;
- рекомендация: `clarify` → `review_top`;
- группа обязательных job-002: `clarify` → `confirmed`.

Вариант `fail` даёт `violated`, а job-003 поднимается с 3-го на 2-е место (общее с job-002).

## Подключение (интегратор / UI)

- **Сервис.** `what_if_options` в отчёт или по запросу. `what_if` — только по явному действию пользователя, результат не сохраняется как решение.
- **UI.** Показывать `summary`, `baseline` и `alternative` рядом и всегда помечать «гипотетически». Числа в JS не пересчитывать.

## Проверки

- `python -m unittest prototype.tests.test_what_if`, 20 тестов:
  - предлагаются только открытые строки;
  - `full` поднимает вакансию, `fail` сдвигает другие;
  - изменение рекомендации видно;
  - спорную строку можно подтвердить;
  - альтернатива совпадает с независимым пересчётом `scoring.score`;
  - отчёт не меняется;
  - неполный запуск остаётся неполным, в том числе без списка `unprocessed`;
  - отклоняются неверные вопросы, подделанный балл и чужая политика у любой вакансии, подделанные место и рекомендация, отчёт без `evaluation`;
  - общие места названы;
  - отчёт v1 без evidence поддерживается;
  - одна политика у отчёта и всех вакансий, ответ подписан ею;
  - пустой рейтинг даёт пустой список, повторённый `job_id` отклоняется;
  - только при политике с единицами (v3, иначе skip):
    - противоречивые повторы предлагаются один раз и решаются вместе;
    - повтор `unknown` — один вопрос;
    - повтор без данных не открывает подтверждённую единицу;
    - спорные повторы с разными статусами показаны как `conflict`;
    - две известные политики в одном отчёте не смешиваются.

## Ограничения

- Одно уточнение за раз. Комбинации не перебираются, а одиночные уточнения, меняющие порядок, уже показывает `compare().swings`.
- Код работает на v2 (`draft-2026-11-13-v2`) и на v3 (`draft-2026-11-14-v3`, E11 #29). Порядок слияния #29 и #30 не важен. Тесты единиц v3 до слияния #29 пропускаются.
