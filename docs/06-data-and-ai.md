# Данные и ИИ, если они нужны в кейсе

1. Проверить формат, объём, пропуски, дубли и разрешённое использование данных.
2. Отделить данные для разработки от контрольной выборки. Не настраивать решение по итоговому тесту.
3. Собрать простой baseline до сложной модели: правила, поиск, текущий процесс или простая статистика.
4. Выбрать метрику из регламента. Если её нет — привязать к пользовательской задаче.
5. Проверять качество и ошибки на тех же примерах и условиях для всех вариантов.
6. Отдельно измерять задержку и стоимость, если есть внешний сервис; записывать условия замера.
7. Сохранять версию модели, промпта, данных и параметры запуска в журнале экспериментов.

Для генеративного ИИ подготовить контрольные случаи: обычный ввод, неоднозначный запрос, недостаточно данных, вредоносная инструкция внутри документа и слишком большой вход. Вывод модели не считать доверенной командой; действия и доступы проверять обычным кодом.

Инструменты разработки через подписку и ИИ внутри будущего продукта — разные вещи. Наличие подписки Codex не означает готовый бесплатный API для приложения. Потребность во внешнем API, лимит затрат и допустимость передачи данных определяются после получения кейса.

Не заявлять точность, экономию времени или бизнес-эффект без замера. Синтетические примеры обозначать явно. Таблица для записей — templates/experiments.csv.
