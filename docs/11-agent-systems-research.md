# Агентные системы для адаптации Nanimai

Исследование: 11 ноября 2026. Первичные источники — README и документация репозиториев по ссылкам ниже. Это сравнительный отбор по документированным возможностям, не бенчмарк и не полный аудит исходников. Исчерпывающий просмотр всего GitHub невозможен; просмотрены основные подходящие классы систем. Ничего не установлено и не запущено, код продукта не изменён.

## Условия выбора

- Адаптируем Nanimai, сначала проектируем продукт и пишем спецификацию.
- Три участника; текущие правила Codex разрешают одного помощника одновременно, исследователи и ревьюеры не редактируют код.
- Для делегирования используем существующий вход ChatGPT, без внешних провайдеров и платных модельных API.
- Рубрика: извлечение 16, сопоставление 24, рейтинг 16, проверяемый результат 12, неопределённость/надёжность 12, воспроизводимость 20.
- Направление рейтинга уточняется. Существующие макеты не заменяют требования организаторов.
- Уже настроены Superpowers 7.0.2 и проектные роли Codex. Изменение инструментария должно давать преимущество сверх этой базы.

## Системы спецификации и разработки

Возможности в средней колонке описаны авторами. Выводы справа — наша инженерная оценка применимости.

| [MetaGPT](https://github.com/FoundationAgents/MetaGPT) | Роли виртуальной software company, генерация требований, структур данных, API и кода; конфигурация модельного backend | Концептуально близок запросу «полная команда», но добавляет отдельное исполнение и настройку моделей. Не выбран для нашей адаптации и режима подписки |

## Рекомендация для совместной работы

Один основной процесс: существующий Superpowers + нативные роли Codex. Документы организовать по полезному для адаптации принципу OpenSpec: текущее поведение, изменение, сценарии приёмки, техническое решение, задачи. Это заимствование структуры, а не установленный или проверенный OpenSpec.

Не устанавливать одновременно Superpowers, BMAD, GSD и OpenSpec как конкурирующие управляющие процессы. Если предпочтителен отдельный продуктовый процесс BMAD, сравнить его на одной конкретной задаче спецификации, а затем выбрать один процесс. Установка не является условием написания качественного PRD.

Роли на этапе проектирования:

1. Главная сессия с владельцем — сценарий, границы продукта, решения и спецификация.
2. Ограниченный исследователь — факты о выбранных модулях Nanimai и расхождениях с макетами.
3. Один независимый ревьюер завершённой спецификации — противоречия, пропущенные состояния, проверяемость критериев и реалистичность адаптации.

Исследователь и ревьюер работают последовательно, не пишут код и не создают помощников. Не раздаём роли лишь ради имитации большой команды.

## Как связать процесс с баллами

| Критерий | Артефакт до программирования | Проверка после реализации |
|---|---|---|
| Извлечение, 16 | Схема требований, фактов и ссылок на источник | Правильность извлечения на размеченных примерах |
| Сопоставление, 24 | Таблица четырёх статусов, контекста, синонимов и длительности | Пропуск сведений не становится ложным несоответствием; цитаты подтверждают вывод |
| Рейтинг, 16 | Единая формула, правила равенства, неизвестности и направления | Рейтинг воспроизводим из результата сопоставления |
| Проверяемость, 12 | Экран доказательств и уточняющих вопросов | Переход от вывода к фрагментам обоих документов |
| Надёжность, 12 | Схема состояний и ошибок | Пустые, повреждённые, иначе структурированные документы; отказ модели |
| Развёртывание, 20 | Границы компонентов и зависимости | Чистый запуск, README, Docker, два use case |

Число агентов отдельно не оценивается по имеющейся рубрике. Выбор процесса должен повышать качество этих артефактов и проверок.

## Оценка ИИ-результатов

| Инструмент | Возможности по первичному источнику | Применимость |
|---|---|---|
| [Promptfoo](https://github.com/promptfoo/promptfoo) | Сравнение промптов и моделей, автоматические evals и CI | Приоритетный кандидат для сравнения вариантов сопоставления на одном наборе примеров |
| [DeepEval](https://github.com/confident-ai/deepeval) | Компонентные и сквозные метрики, включая faithfulness, JSON и agent metrics | Альтернатива при удобной Python-интеграции; LLM-судья не заменяет ручную эталонную разметку |

Эти инструменты не являются оркестраторами разработчиков. Их польза для конкурса может быть выше, чем у ещё одного диспетчера агентов. Вызов внешней модели из локального eval-инструмента всё равно передаёт данные провайдеру; перед запуском согласовать допустимость и бюджет. Сейчас ничего не передавалось на модельные API и evals не запускались.

## Предлагаемый проверочный эксперимент — после разрешения реализации

Если возникнет желание сменить систему, сравнить текущую конфигурацию и одного претендента на одинаковой ограниченной задаче в отдельных копиях, с одинаковой моделью, исходными данными и критериями. Измерять время до принятого результата, количество вмешательств человека, реальные дефекты, расход доступного лимита и объём лишних изменений. Не сравнивать только длину красивого плана или число созданных агентов. Пока такого эксперимента не было, оценка эффективности качественная.

## Агентные библиотеки внутри продукта — отдельный выбор

| Система | Подтверждённая возможность | Применимость |
|---|---|---|
| [PydanticAI](https://github.com/pydantic/pydantic-ai) | Типизированный и валидируемый вывод; [документация агента](https://github.com/pydantic/pydantic-ai/blob/main/docs/agent.md) | Кандидат для извлечения фактов и требований, если существующий слой Nanimai этого не обеспечивает |
| [LangGraph](https://github.com/langchain-ai/langgraph) | Граф состояния, persistence, interruption/resumption | Нужен при действительно сложных ветвлениях и возобновляемых процессах; не обязателен для короткой последовательности обработки |
| [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) | Structured outputs, tools, handoffs, программная оркестрация | Подходит при соответствующей модельной инфраструктуре; не требуется лишь ради одного вызова извлечения |
| [CrewAI](https://github.com/crewAIInc/crewAI) | Ролевые агенты, задачи, типизированные Flows и persistence | Не выбран для P0: дополнительные ролевые обсуждения сами по себе не доказывают точность сравнения |
| [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) | Агенты и явные workflows; [описание](https://learn.microsoft.com/agent-framework/overview) | Условный кандидат при потребности в этом стеке, не повод мигрировать существующее приложение |

Ни одна библиотека не обеспечивает правильное HR-сопоставление автоматически. Формат результата и допустимые статусы задаём мы; соответствие цитат источнику проверяем отдельно. Итоговый балл и сортировку рассчитываем кодом по фиксированной методике. Это делает агрегацию воспроизводимой при одинаковых входных оценках, но не устраняет вариативность самого LLM-извлечения.

SDK продукта и coding assistants — разные контуры. В частности, [подписка ChatGPT и API имеют отдельный биллинг](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform). Подписки команды не считаем автоматически модельным backend сдаваемого приложения.

## Уточнение команды и рекомендуемое разделение — 11 ноября

Со слов владельца: Григорий — тимлид и главный продукт, работает в текущей Pro-подписке; Егор также участвует в продуктовой работе, имеет подписку, названную владельцем «Cloud Max» за $100 и модель «Fable 5.2»; Ваня имеет подписку Pro за $100 и доступ к Astra. У подписок есть сбросы лимитов. Названия, тарифы, конкретные инструменты и время сбросов независимо не проверены; не использовать их как подтверждённые публичные характеристики сервисов.

Ниже предложение, не принятое командой распределение. Пользователь просит пока только проектирование и исследование; установки и разработка не разрешены этим документом.

| Участник | Ответственность | Основной процесс |
|---|---|---|
| Григорий | Требования, пользовательский сценарий, общая спецификация, контракты, порядок задач, интеграция и финальная приёмка | Уже установленный Superpowers; единый набор документов в стиле OpenSpec |
| Егор | Сложная логика сопоставления, неизвестность, свидетельства, методика рейтинга; независимая проверка спецификации и чужих изменений | Superpowers в его coding-среде после проверки совместимости; BMAD — альтернатива для продуктово-архитектурной проработки, а не второй одновременно управляющий процесс |
| Ваня | Ограниченный модуль приложения: например загрузка, отображение результатов и API-интеграция по утверждённому контракту | Superpowers executing-plans; GSD Core — альтернатива, если нужен отдельный поэтапный процесс и его делегирование согласовано с правилами проекта |

Разные подписки полезно использовать одновременно, но различие оркестраторов само по себе не гарантирует выигрыш. Предпочтение по умолчанию — общий процесс, разные зоны ответственности; альтернативные системы оценивать по удобству конкретного участника. Три устройства/подписки не означают единую автоматически управляемую отсюда агентную команду. Начать с передачи небольших заданий через общий приватный репозиторий и чат команды; отдельную межмашинную инфраструктуру пока не вводить.

Карточка передачи задачи: ID, цель, разрешённые файлы/модуль, входной и выходной контракт, зависимости, критерии приёмки, проверки, запретные изменения, результат в виде ветки/PR и известных ограничений. Один исполнитель владеет модулем; общие контракты меняются согласованно. Автор не является единственным проверяющим собственной работы.

Для контроля лимитов достаточно списка по участникам: доступен / близок к лимиту / ограничен до указанного времени. Время сброса берётся из интерфейса аккаунта; фиксированный график и точные квоты не предполагаются. Незавершённые задачи передаются с текущим состоянием и доказательствами, без копирования всей переписки.

Первый этап до кода: Григорий собирает требования и сценарий; Егор проверяет методику и крайние случаи; Ваня проверяет состав и запускаемость существующей базы без изменений. Затем фиксируем общую спецификацию и только после этого распределяем реализацию.
