## Предлагаемый сценарий

**Ассистент доказательного сравнения резюме и вакансии для кадровой службы.** Кадровик видит не только итоговый балл, а основание оценки каждого требования и вопросы, которые нужно уточнить у кандидата. Это наше предложение реализации, не дословное дополнительное требование кейсодателя.

1. Загрузить или вставить вакансию и синтетическое резюме.
2. Извлечь требования; дать кадровику проверить их формулировки и обязательность.
3. Сопоставить каждое требование с конкретным фрагментом резюме.
4. Показать таблицу «требование → найденное подтверждение → статус → пробел/вопрос».
5. Сохранить результат и правку кадровика; при необходимости экспортировать краткий отчёт.

Статусы: подтверждено / частично / не соответствует / недостаточно данных. Отсутствие записи в резюме не должно автоматически превращаться в установленное отсутствие навыка. Приоритет — объяснимость и корректное выражение неопределённости; общий рейтинг вторичен. Финальное кадровое решение остаётся у человека.

Пример демонстрационного результата, **вымышленный**:

| Требование | Свидетельство в синтетическом резюме | Статус | Следующий шаг |
|---|---|---|---|
| Python | «Разрабатывал сервис обработки заявок на Python» | Подтверждено | Показать источник |
| SQL | Упоминаний нет | Недостаточно данных | Уточнить опыт SQL |
| Два года релевантного опыта | Описан один год работы | Частично | Проверить другие проекты |

Не выводить соответствие культуре, личные качества или «счастье» из косвенных признаков. Использовать только относящиеся к работе сведения и явные требования.

До старта разрешить эту развилку запуском базового сценария; готовые результаты ИИ в запасном демо помечать как заранее рассчитанные.

## Чем решение должно отличаться от уже готовой платформы

Показать измеримый вклад команды: проверяемые цитаты, корректное «недостаточно данных», требования с подтверждением кадровика, воспроизводимая проверка и аккуратная обработка отказов. Наличие этой комбинации в действующем Nanimai нужно уточнить у товарищей: без frontend и Tulpa нельзя уверенно объявлять её новой для продукта.

В сдаче перечислить: существующие компоненты, сделанные за хакатон изменения, используемые внешние сервисы, источник демонстрационных данных. Простое переименование интерфейса не создаёт самостоятельной ценности для кейса.

## Предлагаемые критерии приёмки

Это внутренние критерии команды, не объявленные веса жюри.

- Сквозной путь от пары документов до таблицы соответствий воспроизводится на втором компьютере.
- У каждого положительного вывода есть проверяемый фрагмент исходного текста; несуществующая цитата считается ошибкой.
- При отсутствии информации система показывает неопределённость; при сбое модели не выдаёт отказ кандидату.
- Правка требования обновляет сравнение; результаты предыдущей версии не выдаются за актуальные.
- Данные разных аккаунтов изолированы, если демо предусматривает несколько пользователей.
- Вредоносные инструкции внутри резюме не меняют правила оценки.
- Ограничены размер файлов и время обработки; скан/нечитаемый файл/ошибка модели дают понятное сообщение.

Предлагаемый небольшой набор оценки: 3 синтетические вакансии и 15–30 синтетических резюме с ручной разметкой требований. Отдельно тестировать подтверждение, противоречие, отсутствие информации, неоднозначные даты и навык без опыта. Часть примеров отложить до финальной проверки. Размер набора — план, готовых данных и замеров пока нет.

Измерять точность статусов на уровне требований, долю неподтверждённых выводов и ошибочных цитат, время сравнения человеком и с инструментом, задержку/стоимость обработки. Сравнить с простым поиском ключевых слов на тех же примерах. Для задачи пары документов эти метрики полезнее рейтинга top-k; ранжирование потребуется только при расширении кейса на набор кандидатов.
