## Результат для продукта

Рекрутер видит, **что именно нужно проверить первым и почему**, и отделяет своё решение от предложения модели. Подтверждение списка требований не превращается в подтверждение смысла всех оценок. Это развивает проверяемость/неопределённость T2/T4/T5, а не обещает автоматический правильный отбор.

Объём: 3–5 часов самостоятельной разработки после E5/E6; ориентир первого полезного PR — 90 минут. Если E5/E6 не завершены, сначала сдаёшь их. E7 сравнение сохраняет приоритет перед дополнительной визуализацией; what-if можно отложить.

## Границы и первый handoff

Ты не один: Ваня реализует экран/транспорт, Codex — хранение/операции/интеграцию. Не откатывай чужие изменения. Твои новые файлы: `prototype/review_queue.py`, `prototype/review_policy.py`, их тесты; синтетические ожидания в `evaluation/expectations/egor/` по согласованному manifest Вани. Изменение contracts/evidence/requirements_review только в своей области и с явным handoff. Не писать web_app, run_store, application, pipeline, model, privacy, Docker/locks.

До большого кода передай в PR короткий контракт двух чистых функций:

- `build_review_queue(report)` — типизированная очередь причин проверки на текущем отчёте;
- `assess_handoff(report, decisions)` — состояние готовности выбранной вакансии к передаче и открытые причины, без файлов/сети/побочных эффектов.

Минимальный элемент очереди: стабильный id, job_id, optional requirement_id, reason_code, priority, source references, объяснение на основе причины и допустимое действие. Стабильность не должна зависеть от порядка входных файлов. decisions — подтверждённые сервисом действия человека на версии источника/списка/отчёта. Не считать произвольный клиентский JSON или текст модели доказательством действия человека. Точные DTO согласовать одним fixture до подключения — не изобретать второй формат отчёта.

## E8.1 · P0 — очередь спорных выводов

1. Собери уже имеющиеся сигналы, не вызывая новую модель: invalid/needs_review из evidence, спорный mandatory, непокрытый текст вакансии, неизвестное обязательное условие, неполная обработка, конфликт условий из E5, сигнал потери профессиональных данных privacy.
2. Различай: технически неверный источник/ссылка; спорная интерпретация; недостающие сведения; конфликт условий; непроверенный состав требований. Не превращай их все в unknown/fail.
3. Приоритет: препятствие целостности → потенциально ошибочное обязательное условие/отрицательный вывод → конфликт условий → остальные уточнения. Для одинакового приоритета порядок детерминирован, но не выдаётся за важность для найма.
4. Покажи необходимый контекст: оба источника и заголовки, если они есть. Не придумывай отсутствующую цитату; источник из privacy остаётся обработанным. Повтор цитаты в противоположных контекстах виден как неоднозначность.
5. Для причины укажи действие: проверить список, прочитать контекст, уточнить у кандидата, принять конфликт условий как осознанное решение HR. Само нажатие «прочитано» не доказывает соответствие требованию.
6. Не отправляй каждую нормальную строку в срочную очередь только потому, что её смысл не доказан алгоритмом. Общий статус model_proposed остаётся, очередь отражает конкретные сигналы. Верни счётчики по причинам/вакансиям, без заявления о точности или сэкономленном времени.

## E8.2 · P0 — допустимые решения и состояние передачи

- `draft` и `reviewed_for_handoff` — разные состояния; второе означает явное решение рекрутера на конкретной версии, а не научно доказанную правильность модели.
- Источник/требования/политика изменились → старые решения stale. Чужая вакансия, повторяющиеся id или неподтверждённая ревизия → invalid.
- Неполный набор не даёт окончательного общего рейтинга; технически неверная цитата не закрывается кнопкой. Требование со спорной обязательностью не возвращается в жёсткую группу без отдельного исправления/подтверждения.
- Подтверждение полного списка требований и подтверждение решения о передаче — отдельные действия. Условия, которые HR принимает как исключение, остаются видимыми в отчёте с решением, не исчезают из истории.
- Отсутствие сведений сохраняется даже после просмотра. `unknown → full` нельзя получить только действием «проверено». Не добавляй ночью ввод неподтверждённого опыта из устного интервью: это отдельный будущий источник.
- Не вводи массовый auto-approve или автоматический отказ кандидату. Изменение старого evaluation не требуется: предложение модели сохраняется, действия человека — отдельный слой.

## E8.3 · P0 — доказательства поведения

Используй готовые E6/V6 fixtures, не создавай второй несовместимый набор. Добавь сценарии, которые ловят реальные ошибки:

1. Полный отчёт с неподтверждённым списком не считается проверенным.
2. Список подтверждён, но остался неверный источник: блокер виден.
3. Чужая вакансия/старый hash/изменённый mandatory не наследуют решение.
4. Unknown остаётся unknown после просмотра.
5. Конфликт удалёнки и офиса остаётся видимым после решения HR.
6. Потеря Rust при privacy не выдаётся за отсутствие навыка.
7. Одинаковая цитата под «Работал»/«Не работал» не разрешается молча.
8. Два одинаковых клика/перестановка вакансий не дублируют очередь.
9. Неполная обработка не превращается в окончательное «ни одна».
10. Отчёт без сигналов не получает искусственно заполненную срочную очередь; общий model_proposed сохранён.

Минимальный артефакт: два JSON-fixture очереди и решений (обычный/спорный), таблица reasons→actions, тесты чистых функций. В `docs/reviews/egor-night-handoff.md` зафиксируй версию политики, ограничения и что должен проверить backend. Не называй собственные ожидания ответами эксперта.
