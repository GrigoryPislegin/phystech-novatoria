# ТЗ Егору: разработка доказательств и требований с Fable

Готовый текст для передачи Егору и его рабочему чату Fable. Обновлено 13 ноября 2026 по поручению Григория: теперь Егор также реализует сложную логику продукта. Прежнее ограничение «не менять код движка» заменено указанным ниже владением файлами. Сроки — ориентиры, МСК.

Работай основной сессией на Fable, доступной в моей подписке. Не выдумывай идентификатор модели: если Fable недоступна, сообщи это и сохрани план; не подключай платный API автоматически. Задание — короткое целевое ревью, затем **рабочий код и регрессионные тесты**. Один документ с рекомендациями не является готовой поставкой.

Твоё ревью PR #2 получено; заново его писать не нужно. Прочитай CLAUDE.md, AGENTS.md, docs/reviews/integration-followup.md, docs/reviews/full-review-2026-11-13.md, docs/18-next-actions.md, prototype/contracts.py, prototype/pipeline.py, prototype/scoring.py и тесты. Ты не один: Codex ведёт приватность, модель, pipeline/CLI, скоринг и сборку; Ваня — документы/CI/второй компьютер. Не отменяй чужие изменения.

Твоя зона: `prototype/contracts.py` (необходимые изменения контрактов), новые `prototype/evidence.py`, `prototype/requirements_review.py`, отдельные `prototype/tests/test_evidence.py`, `prototype/tests/test_requirements_review.py`, синтетические fixtures и свои docs/reviews. Модули чистые и локальные, без сети. `model.py`, `privacy.py`, `pipeline.py`, `scoring.py`, `__main__.py`, Docker и общие зависимости читаешь, но не редактируешь параллельно. Изменения промптов и места включения новых функций передаёшь через `docs/reviews/egor-development-handoff.md`; Codex подключает их. Формулу и четыре статуса соответствия не меняй без зафиксированного решения.

## E1 — ближайшее окно до 12:40, затем заморозка демо

1. В отдельной ветке от общей `codex/cli-recruiter-prototype` сохрани маленький набор **8–10 синтетических случаев** в `docs/reviews/egor-cases-2026-11-13.json` и пояснение в соседнем MD. Не требуется вручную размечать весь набор CV × вакансий.
2. Для случая укажи case_id, вымышленный cv_text/vacancy_text, ожидаемые требования и статусы, цитаты-основания, rationale, `decision_status`: `draft` либо `expert_confirmed`. При неоднозначности — вопрос и допустимые варианты вместо выдуманного эталона. Ни реальные CV, ни API не нужны.
3. Покрой: отрицание опыта; нерелевантное доказательство fail; заголовки «Обязательно/Желательно»; пропуск второго обязательного требования; отсутствие сведений против подтверждённого несоответствия; составное требование/partial; равные оценки; короткая вакансия против подробной; неполный запуск. Формулу сравнения и веса не объявляй согласованными.
4. Когда Григорий даст опубликованный SHA интеграции, повтори `python docs/reviews/egor_review_repro.py`, тесты и оба demo. Отметь, какие твои п. 1/4/5 исправлены, где остались контрпримеры; исходные 2/3 и новые R3/R4 пока открыты. Не проверяй старую базу как новую интеграцию.

Готовность: случаи воспроизводимы без сети; каждый статус имеет смысловое основание либо явную неопределённость; два отчёта понятны рекрутеру, четыре статуса различимы, incomplete нельзя принять за окончательный вывод. До 12:40 — короткий список блокеров демо, а не косметические замечания.

## E3 · P1 — контекст доказательств, первая кодовая поставка

Основное окно реализации — после консультации, с 14:30. До 13:00 можно подготовить регрессии и контракт в своей ветке, не пытаясь успеть весь модуль в замороженное демо.

Проблема: точное слово «Python» из фразы «Не работал с Python» проходит как цитата; нерелевантный факт может обосновать fail. Вложение quote в mandatory_quote не доказывает, что обязательность относится к этому требованию.

Реализуй в contracts/evidence локальные структуры и проверки с привязкой к исходному **обработанному** тексту: факт, требование, цитата, окружающий контекст/позиция, источник. Сначала запиши короткий контракт функций в handoff, затем реализуй в своей зоне. Вход — существующие Facts/Requirements/Evaluation и обработанные тексты; выход — структурированные проверки/причины и необходимость ручной проверки, без побочных действий.

Не подменяй смысл минимальной длиной цитаты, совпадением слова или списком отрицаний. Структурная проверка и человеческое подтверждение смысла различаются. Недоказанный вывод модели сохраняется как непроверенный, не как подтверждённое соответствие; техническая ошибка не становится unknown. `requires_review` — состояние проверки, не пятый статус соответствия.

Приёмка без API:

1. «Не работал с Python» + цитата «Python» не получают отметку подтверждённого full; отрицание видно проверяющему.
2. «Работал с Excel» не становится проверенным основанием fail по Python.
3. SQL под «Желательно» не подтверждается обязательным только длинной цитатой от «Обязательно».
4. Корректный положительный пример проходит структурную проверку; повторяющаяся цитата с разным контекстом не выбирается молча.
5. Выдуманные источник/id/диапазон/цитата отклоняются. Нехватка сведений, ошибка валидации и спорное доказательство различимы.

Нельзя сделать проверки зелёными, скрыв все строки или безусловно отклонив любой документ. Нужны положительный и спорный путь. Остаточные смысловые ошибки описать честно. Крупную смену контрактов не включаем в замороженное в 13:00 демо; продолжай её в своей ветке.

## E4 · P1 — подтверждение списка требований, вторая поставка

Проблема: из «Python обязателен. Go обязателен» модель извлекает один Python, и complete=true/L=100 выглядят как полное покрытие вакансии.

В requirements_review реализуй минимальное локальное подтверждение рекрутером: версия схемы, hash обработанного исходника, hash полного списка требований с обязательностью, явное подтверждение. «Все вакансии обработаны» и «извлечённый список проверен» — разные состояния. По умолчанию список неподтверждённый; модель сама не выставляет человеческое подтверждение. Изменение исходника, добавление/удаление требования и изменение обязательности аннулируют старое подтверждение.

Это однопользовательский CLI, а не аутентификация или цифровая подпись. Не обещай автоматически доказать отсутствие пропусков: нужен видимый неподтверждённый список и возможность сверить/исправить его по полному исходнику локально. Сеть и новая БД не нужны. Файлы подтверждения сохраняет CLI интегратора в закрытом каталоге; твой модуль проверяет структуру и привязку.

Приёмка: пропущенный Go не подтверждается автоматически; корректное ручное подтверждение подходит только своему источнику/полному списку; изменённый источник, требование, обязательность и чужой hash отклоняются. Вакансии подтверждаются независимо; незавершённый запуск не становится полным из-за подтверждения. Сигналы подключает Codex к отчёту/рекомендации; до этого функция явно отмечена как ещё не интегрированная.

## E2 — консультация 13 ноября в 14:00

Опирайся на уже подготовленный бриф. Приоритетные вопросы на конкретных примерах:

- Обязательное требование: стаж 1 год вместо 3 — исключение из рекомендации или повод для обсуждения? Кто подтверждает обязательность?
- Составное требование и неполные сведения: когда partial, когда unknown; можно ли предлагать вакансию при неизвестном обязательном условии?
- Неполный список требований и неполная обработка вакансий: какое предварительное решение допустимо, что обязан подтвердить рекрутер?
- Ранжирование: важнее обязательные условия или общий балл, как сравнивать короткие и подробные вакансии? Что делать при равенстве?
- Как передаётся результат менеджеру; какие материалы и способы обработки разрешены для проверки и сдачи?

После консультации сохрани `docs/reviews/consultation-answers-2026-11-13.md`: вопрос, фактический ответ, источник/время, вывод для продукта, что осталось открытым. Не обещай экономию времени, точность или юридическую допустимость без основания. Личные материалы/переписку не публикуй. Передай Codex изменения требований; общие docs/01-brief.md и docs/12-expert-answers.md обновляет интегратор, чтобы избежать конфликтов.

## Передача результата

Сначала Git status/diff, сохраняй локальную работу. Создай отдельную `egor/evidence-and-requirements` от общей базы. Если свежий SHA интеграции ещё не опубликован, работай с воспроизведениями независимо и укажи базу; общие файлы не переноси вслепую. E3 и E4 сдавай последовательными небольшими поставками. В handoff укажи сигнатуры, примеры входа/выхода, точки вызова в pipeline/CLI, нужные изменения SYSTEM и совместимость fixtures. Не копируй целиком чужие модули как предложенный patch.

Сначала воспроизведи ошибку тестом, затем исправь. Запусти `python -m unittest discover -s prototype/tests -v`, `python -m prototype demo` и `python -m prototype demo --scenario disputed`. Если новая схема требует миграции fixtures вне твоей зоны, передай минимальное изменение интегратору и перечисли непроходящие проверки. После реализации — одно независимое read-only ревью; Fable основной сессией пишет и исправляет код. Максимум один помощник одновременно, без API продукта.

В передаваемом задании разрешено коммитить **свою кодовую зону и документацию**, запушить отдельную ветку в `GrigoryPislegin/hackathon-phystech-nanimai`, открыть PR в `codex/cli-recruiter-prototype`; без force-push общей ветки и автоматического merge. Передай PR, SHA, команды и фактические результаты. .env, ключи, личная память, реальные CV и приватные отчёты в поставку не входят. Новых API-ключей и платных прогонов для E1/E3/E4 не нужно.
