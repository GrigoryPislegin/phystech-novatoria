## E5 — завершить политику и передать пригодный контракт

Сначала передай то, что уже сделано по скорингу, с formula/policy_version, примерами и тестами. Новое сообщение владельца: правильной единственной перестановки вакансий нет, важны прозрачные критерии и основания. Это не разрешение подгонять веса отдельно под каждую вакансию или объявлять любую модельную оценку правильной.

В письменной политике зафиксируй обязательные/желательные, unknown/partial/fail, составные требования, ничьи, сопоставимость короткой/подробной вакансии, неподтверждённые требования и условия итоговой рекомендации. Для спорного пункта — выбранное правило, основание и ограничение; неподтверждённый экспертный ответ остаётся draft.

Регрессии: перестановка входов/id/файлов не меняет смысловую оценку; одинаковое правило на всём наборе; усиление подтверждённого факта не уменьшает его вклад; отсутствие данных не становится доказанным fail; неполный набор не даёт окончательное «ни одна»; смена версии/требований делает подтверждение stale. Не снижать все неопределённые случаи в один отрицательный статус ради красивого ранжирования.

## E5a — конкретные правки PR #3 до подключения

1. `requirements_review.summarize`, строки 173–178: ключ словаря и `ApprovalCheck.vacancy_id` могут различаться; сейчас чужая confirmed-проверка подтверждает ожидаемую вакансию. Identity mismatch → invalid, final_allowed=false; отдельная регрессия.
2. `requirements_review.check/_changes`, строки 127–160: дубли id в approval сворачиваются dict; approve двух r1 может подтвердить уникальный список по последнему r1. Проверить уникальность сохранённого и текущего списков до сравнения, добавить позитивный контроль.
3. `evidence.verify_span`: изменённые sentence/heading проходят при правильных hash/offset/quote. Либо проверять вычисленный контекст, либо контрактом убрать доверие к сохранённому контексту и пересобирать его из source для UI.
4. `layout` LRU: согласовать с интегратором кеш на один запуск/очистку. Долгоживущий локальный сервер не должен бесконечно хранить старые резюме. Не отменять ускорение пересчётом разметки на каждой строке.

Это воспроизводимые находки независимого исследования нового PR, а не повторение старого ревью. `structure_ok` по-прежнему не доказывает смысл; сохрани честную пометку `model_claim_unverified`. Модуль подтверждения списка не должен сам подтверждать смысл оценки или давать автоматический отказ.

## E6 — закрыть смысловую часть рубрики (24 + части 16 баллов)

После текущей поставки совместно с fixtures Вани отобрать небольшой проверочный набор в трёх областях кейса: frontend, учёт основных средств, образовательный процесс. Синтетика, не новые реальные CV и не платные запросы. Твоя роль — смысловые ожидания и допустимые альтернативы, не изготовление десятков PDF.

Проверить синонимы и уровни задач, длительность/пересечение опыта, образование, «изучал» против «делал», неизвестное, составные требования и непрямое подтверждение навыка. Для каждого ожидаемого статуса — фрагмент и обоснование. Если допустимо несколько статусов/порядков, запиши условия допустимости. Не выдавай draft за мнение эксперта. Нужен новый holdout-набор после фиксации политики; не править веса по каждому его примеру.

Выход: короткий protocol качества и результаты на сохранённых ответах (если они есть), ошибки по типам, нагрузка needs_review. Можно использовать keyword baseline Вани, но сравнение на одном наборе и с одинаковыми правилами. Live для оценки запускает Codex отдельно в разрешённом режиме. Твои старые 60 000 случайных структурных проверок не называем измерением смысловой точности.

## E7 — объяснение различий и полезный what-if

После E5/E6, если P0 готов. Сделай чистую функцию объяснения пары вакансий на рассчитанной политике: какая группа обязательности определила порядок; какие 2–3 требования дают разницу; какие неизвестные условия способны изменить вывод. Цитаты/id берутся из результата, не сочиняются новой моделью. Для равенства явно вернуть tie, не придумывать «чуть лучше».

Первая полезная версия what-if: одну неизвестную строку первого кандидата на рекомендацию считать подтверждённой только в гипотетической копии результата, пересчитать той же функцией и показать возможное изменение. Во вход/выход добавить assumption, policy_version, affected_requirement_ids, baseline/alternative. Исходный результат и human confirmations не меняются. Это анализ чувствительности, не прогноз ответа человека, не вероятность найма и не автоматическое изменение статуса.

Приёмка: 0 модельных вызовов, одинаковый результат при повторе, исходник неизменен, показывается только реальный пробел, смена политики аннулирует прежнее объяснение. Ваня отвечает за отображение, Codex — за включение в отчёт. Если не успеваем, сначала объяснение пары, what-if остаётся road map; не рисовать работающую кнопку поверх отсутствующей функции.

## Передача

Сначала закончи текущую самостоятельную поставку; затем исправления E5a, E6 и только затем E7. Отдельные небольшие PR в общую согласованную базу, без force-push/merge. Передай код, фактические тесты, версии и места включения. Общие docs/01-brief.md/12-expert-answers.md обновляет Codex по твоим ответам и расшифровке, не по догадкам.

Формат: сделано → точные команды/результаты → что не подключено → оставшиеся смысловые пределы → SHA/PR. Это предварительный пакет следующих работ; новые вводные консультации могут изменить приоритет, но не отменяют исправление N6/N7.
